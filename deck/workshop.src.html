00 Where this starts

In 2026, AI started solving problems mathematicians could not.

Not competition exercises with known answers — open problems, some of them decades old. The claims arrived faster than the profession could check them, which is the part this workshop is actually about.

August 2026 Ten open problems, about $2,000 of compute

July 2026 “Very rapid and very unsettling change”

Fortune, reporting mathematicians' reactions as another century-old problem fell. The quoted discomfort is not about whether the result is right. It is about not being able to tell.

01 The question underneath the headlines

“An AI solved it.” How would you know?

The same year produced a second, quieter story: the people whose job is to check these results saying, in public, that checking them is getting hard.

Formal verification is not a guarantee

A demonstration this year showed a bug in the verification method could be exploited to accept a false, AI-generated proof. Passing the checker is evidence, not proof of proof.

Science News

The checker may not check what you meant

Kevin Buzzard's objection: Lean can report that AI-generated code is correct while the statement it proved is not the theorem the mathematician had in mind. The formalisation is itself a translation nobody audited.

IEEE Spectrum

So people built a harness

Eleven mathematicians assembled First Proof, a benchmark of unpublished research-level problems, precisely because the existing evidence would not settle the argument. Their preliminary answer: not yet.

UNU C3

Every one of these stories is the same story. A system produced an answer, and the interesting difficulty was not producing it — it was establishing what had actually happened.

That is a measurement problem, and measurement problems have known solutions. This workshop builds one, from nothing, in front of you. By the end you will have an apparatus that can say what an agent did, how reliably it does it, what it cost, and — the hard part — whether its reasoning actually supported its answer.

02 The motivation

You cannot check what you did not record.

Scoring the answer works for a model that emits one string. The moment there are tool calls and multiple turns, the thing you are evaluating is not a string — it is a trajectory, and almost all of it is invisible if you only keep the last box.

What you scoreone string problem→ model→ answer one comparison grades this completely
What happeneda trajectory problem→ model→ tool_call→ tool_result→ model→ tool_call→ tool_result→ model→ submit

Was the answer computed, or asserted? Did the tool agree with the narration? How many attempts did it take? What did it cost? None of this survives a boolean.

One reported number, four separate questions

Axis 01

Outcome

Did it reach the right answer? The only axis most reports answer.

Axis 02

Process

Does the reasoning support the conclusion? No answer key exists for this.

Axis 03

Cost

What did it spend? Per successful solve, not per run.

Axis 04

Reliability

Would it do it again? One run is not a measurement.

The headlines in part 00 report axis 1. The disquiet in part 01 is about axis 2. The next twelve parts build the apparatus that can answer all four — and it turns out you have to build them in that order, because axis 2 depends on having recorded enough to ask.

03 Session 1 begins · harness engineering

A harness is a measurement apparatus.

It is everything that is not the model: task loading, the agent interface, the tool registry, sandboxed execution, the turn loop and its stop conditions, trace recording, config pinning, fault handling, rollout orchestration, verification, aggregation, reporting.

A harness is a measurement apparatus. A judge is one instrument inside it. Harness engineering is what makes the measurement reproducible; judge hygiene is what makes that instrument trustworthy. Neither produces a meaningful number alone.

The one commitment everything else follows from

Everything downstream of execution is a pure function of an append-only event log. Execution and grading are separated by the trace — and that single seam is what makes new verifiers applicable to old runs at no cost, makes the demo network-independent, and turns reproducibility from a claim into something you can do.

The structural proof. grade.py existing as a separate entry point from run.py is what makes the architecture trace-first. If you have to re-run to re-grade, the architecture is wrong — and you will find out the first time you want to ask a new question of an old corpus.

04 The dataset

AIME 2026, via MathArena.

Why a recurring competition

The problems have to postdate the training data of every model under test. A recurring competition supplies a stream of naturally uncontaminated problems; evaluating on a classic set measures memorisation as much as reasoning.

Why competition maths specifically

Because an answer key exists. That makes it the cleanest possible case for teaching where a judge belongs — here you can demonstrate that a judge on answer correctness is the wrong tool, rather than argue about it.

What the agent is given

The problem statement and nothing else. The key is loaded by a separate function that only verifiers call, so the agent code path cannot reach it.

05 The models, and reasoning effort

Three models, each solving once and judging twice.

gpt-5.6-terragemini-3.7-flashgrok-4.6
S1 Solver10 × 8 problems Judgeblinded process Judgeblinded process
S2 Judgeblinded process Solver10 × 8 problems Judgeblinded process
S3 Judgeblinded process Judgeblinded process Solver10 × 8 problems

The diagonal is the design: no model ever judges itself, so self-preference is eliminated by construction. Stated openly on stage: because nothing judges itself, self-preference is therefore excluded from this design rather than measured by it.

Reasoning models, and what “effort” changes

All three solvers are reasoning models: before answering, they produce an internal chain of thought whose length is controlled by an effort setting. More effort means more tokens spent thinking, more latency, and a larger bill. It does not reliably mean a better answer — Kapoor et al. (2025) found higher effort reduced accuracy in most of their runs. That is exactly the kind of fact that is invisible unless effort is pinned and recorded with every trace.

noneNo extended reasoning. The cheapest arm, and the baseline the others have to beat.--effort none
lowBrief deliberation. Often enough for problems the model recognises.--effort low
mediumThe default in configs/models.yaml, and what the 240-trace corpus uses.--effort medium
highLongest chain, highest cost. Whether it is also the most accurate is a question, not an assumption.--effort high
python3 scripts/run.py --config S1 --task aime2026-07 --n 10 --sweep-effort
# one model, one problem, all four arms — each with its own config hash and its own trace file

Effort is part of the pinned apparatus. Each arm is recorded as its own configuration — S1@none, S1@low, S1@medium, S1@high — so resumption does not collide, and so the report can never average two efforts together and call it one number.

09 Build step 4 · the turn loop

Write the loop by hand, once.

A message list, a dict of Python functions, schemas generated from their signatures, and a while loop that calls the model, runs whatever it asked for, appends the results, and repeats until something stops it. Writing it is what makes it possible to say what a framework would have bought — retries, schema plumbing, a history abstraction — and why none of it was needed here.

call model→ tool calls?→ run each tool→ append results

↶ and around again, until one of these fires

submit_answerThe only clean exit. Arrives as an exception because it is control flow, not an error.
turn / spend capA crude stop condition standing in for a real one — and visible as such.
provider faultRecorded, never retried away. It becomes an outcome.

Note what the loop cannot do: decide whether the answer was right. It has no key and no way to get one. That is not an oversight — it is the isolation that makes the grade a separate, later, cheaper step.

12 Build step 7 · the outcome taxonomy

Seven outcomes, not two.

Done wrong outcome = (answer == key)  →  a provider timeout is recorded as a wrong answer

13 Build step 8 · orchestration

Resumption, and the retry you must not write.

A batch killed half way through and restarted must not duplicate work and must not lose it. Because the store is append-only and keyed, resumption is a read — no bookkeeping table that can drift out of step with the data. And the tempting bug: retrying a rollout that errored until it succeeds. Do that and the error rate is zero, accuracy is up, and both numbers are fiction.

14 Build step 9 · the metrics

One run tells you what an agent can do. Ten tell you what it will do.

pass@k is the probability that at least one of k attempts succeeds — it rises with k and flatters everything. pass^k is the probability that all k succeed. The gap between the two curves is the whole reliability story, and reporting the first without the second is the most common way an agent evaluation overstates what it measured.

pass@k  ·  at least one of k succeeds pass^k  ·  all k succeed

Schematic — exact algebra for a single task at p = 0.70, so shape rather than result. τ-bench put published pass^8 below 25% in retail for the best agent of 2024.

16 The transition

And the fourth question is still completely open.

A run got the right answer. Was the reasoning correct? Nothing built so far can tell us — and nothing built the same way ever will, because there is no answer key for that question.

What a right answer does not prove

The tool computed it and the narration took credit. The chain contained an error that cancelled. It guessed and got lucky. All three look identical from outside, and all three are in the corpus.

What we do have

A complete trace of what actually happened, for all 240 runs, already on disk. Everything from here is a new question asked of an old corpus — at no cost, which is the payoff for the last nine parts.

Answer key existsuse code answer equivalencetool replayexact, free, reproducible
No answer keyuse a judge does the reasoning support the conclusion?

This is the only question in the whole stack where a language model is the right tool — and the rest of the workshop is about using it correctly.

17 Session 2 begins · what we are about to judge

A reasoning trace is not a proof. It is a record of an attempt.

What the judge will read is the interleaving the harness recorded: what the model said, what code it ran, what that code printed, and what it said next. Not a polished write-up — the actual sequence, including the steps that went nowhere.

Reasoning effort changes what there is to judge

At none there is barely a chain to assess; at high there is a long one, most of which may be irrelevant to the conclusion. A judge that rewards length will rank the arms by effort rather than by soundness — which is one of the reasons the rubric below has discrete anchors and demands a quoted span.

The claim, stored beside the evidence

submit_answer(value, reasoning) records what the model says it did. The event log records what it did. When those two disagree, you have found something — and you can only find it because both were kept.

Narrationturn 1 “Let me compute this directly…”
Tool codewhat it ran print(sum(n for n in range(1,500) if n%7==3)%1000)
Tool stdoutwhat came back 608
Narrationturn 2 “The computation gives 615…”the tool and the story disagree

This is the shape of a right-answer-wrong-reasoning case. The submitted value is correct; the reasoning offered for it cites a number the tool never produced. An outcome-only report scores this as a success.

18 Where a judge belongs

Deterministic where you can. Judged where you must.

The most common misuse of a judge is deploying one where code would do — and answer correctness in competition mathematics is exactly that case. Judges belong on the process question, one layer up.

Deterministic

Answer equivalence

Normalise to an integer and compare to the key. Exact, free, reproducible. A judge here is demonstrably the wrong tool.

Deterministic

Tool replay

Re-execute every logged call and diff. Catches hallucinated tool results, and tools that produced the answer the narration takes credit for.

Judged × 2

Process judge

Does the reasoning support the conclusion? No answer key exists for this question. The only layer where a judge is the right tool.

Quasi-mechanical

Masked continuation

Strip the answer, continue from the reasoning, compare the landing point. Asks for a consequence, not an opinion — so it is a control on the judges rather than a third one.

Report the escape rate

Every time the deterministic check cannot decide and you fall through to something fuzzier, that is an escape. The rate bounds and discloses exactly how much of the headline number was not decided by code.

Two added lines. That is the entire blinding experiment.

Note what is absent from the blinded form: the submitted value, the answer key, the outcome, every model identifier, the config hash, seeds, timestamps, usage and provider error strings. The unblinded arm is the same function with a flag. That is deliberate: if the two conditions were built by different code, any difference between them could be a difference in the code.

20 Blinding

Blind the judge to the outcome.

A process judge that can see the answer was correct will rationalise flawed reasoning as sound. This is the largest and least-known failure in the setup, and it is demonstrated on the same traces rather than asserted.

Goes into the prompt

  • problem statement
  • the reasoning
  • tool code
  • tool output

Stripped, and asserted absent

  • the submitted value
  • the answer key
  • the outcome
  • model identifiers
  • config, seeds, timestamps
  • usage and error strings
A bug we found in our own blinding

The first version replaced the submitted value in the narration with [REDACTED]. But that only fires when the narrated value matches the submission — which is exactly when the narration is faithful. The marker appeared on sound traces and never on flawed ones: a judge could read the verdict off a placeholder. Blinding that introduces a tell is worse than none, because it looks careful.

{{CODE|verifiers/process_judge.py|_audit|hard failures, and the one honest soft flag}}
Outcome leakage

Removed by stripping the answer and the verdict. Measured by the ablation, not assumed away by the redaction.

Provenance leakage

Model names and system identifiers removed. Judges favour text that looks like their own, and preference leakage inflates verdicts across a whole family.

Position bias

In any pairwise comparison, randomise position and average over both orderings. Systematic, varies by judge — large, and free to remove.

21 The rubric

Discrete anchors. A mandatory span. Rejected at parse time.

Done wrong

“Rate the reasoning from 1 to 10.” Models do not use the middle of numeric scales consistently, so a 7 from one judge is not a 7 from another and scores stop being comparable across items.

ESTABLISHESThe reasoning is sufficient to determine the conclusion.
INCOMPLETENo error, but gaps remain before a conclusion follows.
ERRORA specific, locatable mistake.
INDETERMINATESupports no determinate conclusion at all.

And a quoted span, always. It is the cure for hallucinated criticism: a judge that cannot point at the step it objects to has not found one. “No verdict” has to mean rejected, not quietly coerced into a default — a rejected verdict is visible in the counts, a defaulted one becomes data.

22 The rotation

Two judges, from different families, never itself.

No self-judging

Self-preference is eliminated by construction rather than corrected afterwards. Judges favour text that looks like their own, and rubric anchors do not fix that.

Severity is comparable

Each model judges in exactly two roles, over two independent solver populations, so a consistently harsh model shows up in both.

The limitation, said first

Because nothing judges itself, self-preference cannot be measured here. It is excluded, not quantified. Say it on stage rather than let it be raised in Q&A.

23 Judging the judges

An unvalidated instrument is not a measurement.

Inter-judge agreement — as a headline

Raw agreement and Cohen's kappa, because raw agreement on a skewed label distribution flatters every judge. Presenting a process score while the instrument disagrees with itself is the failure this prevents.

Judge severity

Each model's rate of not saying ESTABLISHES, across both of its judging roles.

Blinding effect

The same traces judged both ways. Showing the judge that the answer was right made it measurably more forgiving of the reasoning.

Judge–human agreement

Forty traces, sampled stratified across the three solver configurations and across correct and incorrect outcomes, labelled by hand on the same rubric with the same span requirement. Reported per judge, never averaged, with n attached.

Declared on stage

Forty traces labelled by one person is single-annotator calibration, not an annotation study. Until the labels exist, report.py prints that every process figure above it is an assertion rather than a result.

25 Running it

Every command, in order.

One line runs the whole study

scripts/pipeline.py runs the standing check, the rotation corpus, the reasoning-effort sweep, offline grading and the report — in that order, stopping at the first failure. Each stage is literally the command you would have typed, run as a subprocess, so there is no second implementation that can drift from the real one.

Rehearse it offline — no keys, no network

python3 scripts/pipeline.py --mock

720 solver rollouts and about 1,500 judge calls in roughly twenty seconds. Traces produced this way are marked simulated: true, carry their own config hash, and every report built from them prints a banner.

Measure one rollout before spending

python3 scripts/pipeline.py --smoke

One rollout per model at high effort. Read the USD column, multiply by the rollout count the next command prints, and decide. A reasoning model at high effort can emit an order of magnitude more output tokens than a cheap arm, so this is the only honest way to estimate the bill.

The real study

python3 scripts/pipeline.py
# prints the plan, then waits for you to type 'run'

What one line does not do

The 40-trace calibration needs a human, so the pipeline stops short of it and says so. A pipeline that automated this would emit judge–human agreement numbers with nothing behind them.
